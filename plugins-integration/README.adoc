= Ultima Nexus - Integration Module
:toc: preamble
:toclevels: 2

Compatibility aggregators that apply otherwise-independent convention plugins from one classloader.

== Overview

The `plugins-integration` module provides aggregator plugins that must apply two or more third-party Gradle plugins from the *same* convention-plugin classloader, because applying them from separate published modules triggers an upstream bug:

* **Application with jOOQ**: Applies the Vaadin and htmx frontend bundles together with jOOQ codegen

Every plugin here is a temporary compatibility shim. The modules it bridges (`plugins-frontend`, `plugins-persistence`) remain fully independent and standalone; this module — and each plugin in it — is deletable once the upstream issue it works around is fixed.

== Installation

Add to your version catalog (`gradle/libs.versions.toml`):

[source,toml]
----
[versions]
ultima-nexus-plugins = "latest.release"

[plugins]
ultimanexus-jvm-bundle-application-with-jooq = { id = "dev.daymor.ultimanexus.jvm.gradle.bundle.ultima-nexus-jvm-application-with-jooq", version.ref = "ultima-nexus-plugins" }
----

== Application with jOOQ Bundle

Use this bundle instead of applying the frontend bundles and `feature.jooq-codegen` separately, whenever a single application needs both a Vaadin (or htmx) frontend and jOOQ code generation.

=== Usage

[source,kotlin]
----
plugins {
    alias(libs.plugins.ultimanexus.jvm.bundle.ultima.nexus.jvm.application)
    alias(libs.plugins.ultimanexus.jvm.bundle.application.with.jooq)
}
----

* `dev.daymor.ultimanexus.jvm.gradle.feature.jooq-codegen`

=== Why It Exists

Vaadin's `flow-gradle-plugin` (https://github.com/vaadin/flow/issues/17665[vaadin/flow#17665]) computes the inputs of `VaadinPrepareFrontendTask` (`svc`, `tokenService`, `inputProperties`) only in its `project.afterEvaluate`. When the Vaadin plugin and the jOOQ codegen plugin are contributed by two *different* published convention-plugin modules, applying both to the same project perturbs the `afterEvaluate` ordering enough that the Vaadin task is realised before those inputs are set — failing the build with `property 'svc' … doesn't have a configured value`.

Applying them from one module (one classloader) keeps the ordering intact. This aggregator is the only place `plugins-frontend` and `plugins-persistence` are deliberately coupled.

NOTE: Remove this module when the upstream Vaadin bug is fixed; the frontend and persistence plugins can then be applied side by side directly.
